GPU 粒子：一次 draw 画两万个光点，顺便解决"软"和"乱序"

粒子看着像"模拟"，其实大半是渲染问题：怎么把一个小四边形永远朝向相机、怎么和场景正确遮挡、 怎么在几十倍 overdraw 下还不爆掉、透明要不要排序。本页的每个粒子都没有状态 —— 位置是 seed 和时间的闭式函数，顶点着色器现场算出来，一个字节都不用回传。

1. 无状态粒子：位置不存，是"算"出来的

// seed 是每个粒子唯一的常数；life 是自己循环的寿命
float life = fract(u_time * 0.22 * (0.6 + 0.9 * s.x) + s.y);
vec3  c    = 起点 + 上升(life) + 螺旋(life) + 抖动;

// 顶点着色器里把四边形展开成永远朝向相机的 billboard：
// 在裁剪空间偏移，乘 clip.w 之后屏幕尺寸就与距离无关
vec4 clip = u_vp * vec4(c, 1.0);
gl_Position = vec4(clip.xy + a_corner * u_size / u_res * clip.w, clip.z, clip.w);
  1. 没有 ping-pong、没有 transform feedback。 只要轨迹能写成时间的函数（火焰、尘埃、魔法、雨雪）， 就不需要保存上一帧的状态，GPU 侧零显存、零同步，改一下 u_time 就是另一帧。
  2. 代价是"不能相互作用"。 粒子之间要碰撞、要被上一帧的力场推动，就必须有状态 —— 那才是 transform-feedback.html 那条路。
  3. billboard 为什么在裁剪空间挤？ 因为裁剪空间的 x/y 就是屏幕方向。乘 clip.w 抵消透视除法， 得到"屏幕像素尺寸恒定"；不乘就是"世界尺寸恒定"，远处会变小。

2. 软粒子：拿场景深度当剪刀

float sceneZ = linearDepth(texture(u_depth, gl_FragCoord.xy / u_res).r);
float partZ  = linearDepth(gl_FragCoord.z);
if (partZ > sceneZ + 0.05) discard;                       // 被挡住 → 手动深度测试
float soft = clamp((sceneZ - partZ) / u_soft, 0.0, 1.0);   // 撞到表面 → 淡出，不再"切一刀"

粒子这一趟故意不挂深度附件，因为要一边深度测试一边采样同一张深度图就构成 feedback loop（未定义行为）。 改成在 FS 里手动比较深度：代价是被挡住的粒子也照跑片段着色器（丢了 early-Z）， 好处是可以顺手做软边，而且和绘制顺序无关。想省回来就得自己分块剔除，或者把深度拷一份用。

3. 加色 vs 透明：排序到底要花多少

  1. 加色混合可交换（a+b = b+a），所以不用排序、不用回读，随便画。 火焰、光晕、能量全都用它，这不是"省事"，是数学上就不需要。
  2. alpha 混合不可交换，理论上必须从远到近。而本页粒子没有位置缓冲 —— 排序意味着CPU 把两万个粒子的轨迹再算一遍、排序、然后每帧重传实例缓冲。 把「顺序」切到排序，看右下角 CPU 时间和带宽怎么跳。
  3. 但要先问"错多少"。 顺序带来的误差是 a₁·a₂·Δ颜色 —— 两个都接近透明的软粒子叠在一起时， 它只是二阶小量，所以市面上的烟雾/尘埃经常干脆不排序。一旦粒子接近不透明（勾「硬粒子」）， 顺序立刻变成硬遮挡，这时候不排序就是穿帮。先算误差，再决定要不要为排序付那份 CPU。
  4. overdraw 才是粒子的性能大头。 切到热力图：一个像素被几十个粒子盖住， 每个都要跑完整的 FS（采样深度、算软边）。所以粒子渲染的优化永远是"少算几个像素"： 缩小屏幕占比、近处淡出、用低分辨率层、把粒子画在降采样的缓冲上。
