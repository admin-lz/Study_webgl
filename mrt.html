MRT / 延迟着色：先把几何信息摊到几张图上，再统一算光照

前向渲染里光照是按物体算的：100 个物体 × 40 盏灯 = 4000 次光照计算，还得把物体重画一遍。 延迟着色把顺序倒过来 —— 一遍把 albedo / 法线 / 位置画进 G-buffer（这就是 MRT：一次 draw 写多张附件）， 然后一张全屏 pass 按像素算光照：复杂度变成"像素 × 灯"，跟物体数量无关。

1. 一次 draw，写多张附件

// FBO：3 张 RGBA8 + 1 张位置附件 + 一张可采样的深度纹理
gl.framebufferTexture2D(gl.FRAMEBUFFER, gl.COLOR_ATTACHMENT0, gl.TEXTURE_2D, rtAlbedo, 0);
gl.framebufferTexture2D(gl.FRAMEBUFFER, gl.COLOR_ATTACHMENT1, gl.TEXTURE_2D, rtNormal, 0);
gl.framebufferTexture2D(gl.FRAMEBUFFER, gl.COLOR_ATTACHMENT2, gl.TEXTURE_2D, rtMat,    0);
gl.framebufferTexture2D(gl.FRAMEBUFFER, gl.COLOR_ATTACHMENT3, gl.TEXTURE_2D, rtPos,    0);
gl.framebufferTexture2D(gl.FRAMEBUFFER, gl.DEPTH_ATTACHMENT,  gl.TEXTURE_2D, rtDepth,  0);
gl.drawBuffers([COLOR_ATTACHMENT0, 1, 2, 3]);   // ← 少写这句，多出的附件就是"废的"
// 片元着色器：每个 out 变量对应一个 attachment
layout(location = 0) out vec4 gAlbedo;
layout(location = 1) out vec4 gNormal;
layout(location = 2) out vec4 gMaterial;
layout(location = 3) out vec4 gPosition;

drawBuffers 是 MRT 最容易漏的一步：不写它，默认只写 COLOR_ATTACHMENT0，其他附件一律是未定义内容。

2. 位置到底存不存？

  1. 位置可以不存：用深度纹理 + gl_FragCoord 反投影出来，省一张附件。 
    vec4 ndc = vec4(uv * 2.0 - 1.0, depth * 2.0 - 1.0, 1.0);
vec3 world = (u_invViewProj * ndc).xyz / (u_invViewProj * ndc).w;
  2. 也可以存：写起来直观，但格式选错就出事。世界坐标范围是 ±20 这种量级， RGBA8 只有 256 级 → 每级约 0.16 个单位，光照里会看到明显的条纹和块状跳变。
  3. RGBA16F / RGBA32F 精度够，但每像素 8 / 16 字节。1920×1080 下，32F 存位置一张附件就是 8.3 MB， 而且 G-buffer 要"写一遍 + 读一遍"，实际带宽翻倍。切上面的下拉框能直接看到量化带来的差别。

3. 延迟着色的代价

  1. 透明物体没地方放。G-buffer 每像素只能存一份几何信息，"一层"就是它最大的限制。 半透明只能退回前向渲染，再叠加到结果上。
  2. 带宽换计算。好处是光照与物体数解耦，坏处是 G-buffer 的读写带宽很大 —— 这也是为什么移动端更爱 Tile-based Deferred（把 G-buffer 放在片上）或者干脆继续前向。
  3. MSAA 变贵。G-buffer 每张附件都要按采样数放大，而且法线/AO 这类数据要单独 resolve。
  4. 看不到的像素也在算。G-buffer 覆盖了屏幕所有像素，被遮挡的物体照样写进去。 所以重场景里常常先做一遍深度预 pass（depth prepass）再着色。
