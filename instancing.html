实例化：把「N 个物体」变成「1 次 draw + N 份差异」

一万株草，几何完全相同，只有位置、朝向、高低、颜色不一样。逐个 draw 就是一万次 JS→GL 的往返； 把它们那份「差异」放进缓冲，让顶点着色器自己按实例号去取，就只剩一次 drawElementsInstanced。 本页三种写法可以随时切换 —— 画面像素级相同，差别全在 CPU 提交和 GPU 取数方式上。

1. 实例化只加了两样东西

// ① 告诉 GL：这个 attribute 不是"每顶点取一次"，
//    而是"每实例取一次"（divisor = 1）
gl.vertexAttribPointer(aXform, 4, gl.FLOAT, false, 32, 0);
gl.vertexAttribDivisor(aXform, 1);   // ← 关键就这一行

// ② 一次 draw 画 N 个实例
gl.drawElementsInstanced(gl.TRIANGLES, 18, gl.UNSIGNED_SHORT, 0, N);
  1. 几何只上传一份。 一株草 = 8 个顶点 / 6 个三角形，显存里只有这一份； 一万株不需要一万份顶点，只需要一万份 32 字节的「差异」（位置、朝向、高度、颜色、相位）。
  2. draw call 从 N 变 1。 每个 draw call 在驱动里都有固定开销：状态校验、命令打包、提交到 GPU。 N=10000 时这个开销通常是毫秒级，而 GPU 本身可能只花了几十微秒 —— 也就是 CPU 成了瓶颈。
  3. 顶点着色器照常跑 N×8 次。 实例化省掉的是"提交"，不是"计算"： 顶点处理和光栅化的工作量一个不少，实例化不是 LOD，也不是剔除。

2. 同一个「差异」，三种取法

// A. 逐个 draw：差异走 uniform（每画一株改一次 uniform）
for (i = 0; i < N; i++) {
  gl.uniform4fv(uXform, data, i*8, 4);
  gl.uniform4fv(uTint,  data, i*8+4, 4);
  gl.drawElements(TRIANGLES, 18, UNSIGNED_SHORT, 0);
}

// B. 实例属性：差异走 divisor=1 的 attribute
layout(location = 1) in vec4 i_xform;
// C. 数据纹理：差异走 texelFetch，用 gl_InstanceID 当索引
int i0 = gl_InstanceID * 2;
vec4 X = texelFetch(u_inst, ivec2(i0 % u_w, i0 / u_w), 0);
vec4 T = texelFetch(u_inst, ivec2((i0+1) % u_w, (i0+1) / u_w), 0);

三种写法在本页画出来的像素完全一样（同一份数据，只是搬运方式不同），但成本曲线不一样：
A 的 CPU 开销 ∝ N，一万一株就废了；B 是现在的主流，属性带宽高、延迟低；
C 是 WebGL1 时代的兜底（那时没有 divisor），现在依然有用 —— 实例数上百万时，一张纹理比一堆 attribute 更好管理， 代价是取数要过纹理单元，而且显存会被行宽padding 撑大。

3. 实例化解决不了什么

  1. 每个实例换贴图 / 换 program。 实例化是"一次 draw 一个状态"，所以同一次 draw 里只能共用同一套 shader 和纹理。 要按实例换贴图，得靠纹理数组 / 图集 / bindless，或者 multiDrawElements 分组。
  2. 剔除。 实例在 VS 里只是被搬到世界空间，被裁掉的实例照样跑完整个顶点阶段。 要真省下来，得在 CPU 侧把可见实例挑出来重排缓冲（或者用 VS 把不可见的顶点退化，但那只省光栅化）。
  3. 排序 / 透明。 实例在缓冲里的顺序就是绘制顺序，透明混合要正确就得按深度重排整份实例数据，每帧重传。
  4. 阴影。 阴影 pass 要把同一份实例缓冲再画一遍（换灯光 VP），所以实例化对阴影管线的收益是翻倍的 —— 这也是它几乎必用的原因。
