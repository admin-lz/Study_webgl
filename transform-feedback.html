变换反馈：把顶点着色器的输出存回缓冲，让 GPU 自己迭代状态

顶点着色器正常只有一条出路：光栅化。变换反馈（Transform Feedback）给它开了第二条路 —— 把 varying 写进一个 buffer，下次再把这个 buffer 当顶点数据读回来。 不需要 compute shader，就能在 GPU 上跑一个"粒子积分"：状态在显存里，CPU 什么都不用管。

1. 一次"跑在 GPU 上的物理步"

// 链接之前必须声明要捕获哪些 varying —— 链接之后再调是无效的
gl.transformFeedbackVaryings(progSim, ["v_pos", "v_vel", "v_life", "v_seed"],
                             gl.INTERLEAVED_ATTRIBS);
gl.linkProgram(progSim);

// 把输出缓冲绑到 TF 的 0 号槽（注意和 uniform 的槽位是两套体系）
gl.bindTransformFeedback(gl.TRANSFORM_FEEDBACK, tf);
gl.bindBufferBase(gl.TRANSFORM_FEEDBACK_BUFFER, 0, nextBuf);
gl.enable(gl.RASTERIZER_DISCARD);           // 纯计算：不光栅化，省一大截
gl.beginTransformFeedback(gl.POINTS);
gl.drawArrays(gl.POINTS, 0, count);         // 顶点数就是粒子数
gl.endTransformFeedback();
gl.disable(gl.RASTERIZER_DISCARD);
  1. 顶点着色器里照常算物理，把结果写进 out；光栅化被丢掉，只有 varying 被存下来。
  2. 不能读写同一块缓冲。所以必须 ping-pong：这一帧读 A 写 B，下一帧读 B 写 A。
  3. gl_Position 还是要写（给个 vec4(0.0) 就行），否则行为未定义。
  4. 捕获的 INTERLEAVED 排布就是 varying 声明顺序：这里是 3+3+1+1 = 8 个 float，正好和输入的顶点布局一致 —— 所以同一块 buffer 既能当输出、又能当下一次迭代的输入。
  5. 踩过的坑：TF 输出缓冲不能同时是"当前绑定的 ARRAY_BUFFER"。踩中了 drawArrays 会直接 INVALID_OPERATION，而且不报任何别的信息 —— 每次迭代前把 ARRAY_BUFFER 解绑最省心。

2. 回读为什么要等

const fence = gl.fenceSync(gl.SYNC_GPU_COMMANDS_COMPLETE, 0);
gl.flush();
// ... 这一帧里可以做别的事 ...
gl.clientWaitSync(fence, gl.SYNC_FLUSH_COMMANDS_BIT, 0);
gl.getBufferSubData(gl.TRANSFORM_FEEDBACK_BUFFER, 0, dst);  // 现在才是最新的

GPU 是异步的：drawArrays 返回时数据还没写出来。同步回读（直接 gl.readPixels / getBufferSubData） 会让 CPU 卡在等 GPU，这就是所谓的"同步点"，是性能杀手。所以真实引擎里回读要尽量少、尽量晚。 本页默认每帧回读前 512 个粒子只是为了画右下角那张图证明状态在 GPU 上；把开关关掉，粒子照常飞。

3. 什么时候用 TF

  1. 粒子 / 布料 / 群体模拟：状态简单、每个粒子独立、不需要粒子间通信。
  2. GPU 剔除 / 变形缓存：先跑一遍视锥剔除或骨骼蒙皮，把结果存下来给后续 pass 复用（比如把蒙皮后的顶点喂给阴影 pass）。
  3. 不能做的事：没有随机写入、没有原子操作、没有粒子间通信 —— 这些要等 compute shader（WebGPU / WebGL 没有）。 散列表、排序、粒子碰撞这类需求，TF 干不了。
  4. 和 WebGPU 的关系：在 WebGPU 里这件事直接用 compute shader 做，代码更直白（能读写 storage buffer、有 workgroup 共享内存）。 但 TF 在 WebGL2 里是唯一的选择，理解了它也就理解了"GPU 上的状态迭代"这件事本身。
